# UI Coding Standards

## The Rule

**Only shadcn/ui components may be used for UI in this project. Custom components are NOT permitted.**

Every visible UI element (buttons, inputs, cards, dialogs, tables, selects, calendars, etc.) must come from shadcn/ui. If you need a UI element, find the matching shadcn component and use it as-is.

## Adding Components

- Install components with the shadcn CLI: `npx shadcn@latest add <component>`
- Installed components live in `src/components/ui/` and are imported via the `@/components/ui/...` alias.
- Browse the available components at https://ui.shadcn.com/docs/components before concluding something is missing.
- Do not hand-write files in `src/components/ui/`. They must be generated by the CLI.
- Do not modify generated shadcn files to change behavior or add features. Configure components through their documented props, variants and `className`.

## What Is NOT Permitted

- Creating new reusable components (e.g. `StatCard`, `WorkoutCard`, `PageHeader`) in `src/components/` or anywhere else.
- Wrapping shadcn components in your own abstractions or "wrapper" components.
- Building UI from raw HTML elements (`<button>`, `<input>`, `<select>`, `<table>`, etc.) when a shadcn equivalent exists.
- Installing other UI libraries (MUI, Chakra, Ant Design, Mantine, etc.) or unstyled primitives used to build bespoke components.
- Copy-pasting and restyling a shadcn component under a new name.

## What IS Permitted

- Composing shadcn components directly inside pages and layouts (`src/app/**`), e.g. `Card` + `CardHeader` + `CardContent` + `Button`.
- Layout and structure with plain semantic elements (`<main>`, `<section>`, `<div>`) styled with Tailwind utilities. These hold shadcn components. They do not replace them.
- Typography with plain elements (`<h1>`, `<p>`) styled with Tailwind utilities, where shadcn has no equivalent.
- Next.js file conventions (`page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`), which are routes and not custom components.

## Styling

- Use Tailwind CSS utility classes and the shadcn theme tokens (`bg-background`, `text-muted-foreground`, `border`, etc.) defined in `src/app/globals.css`.
- Use the variants and sizes a component already provides (e.g. `Button variant="outline" size="sm"`) before reaching for `className` overrides.
- Merge conditional classes with the `cn()` helper from `@/lib/utils`.
- Do not hard-code colors (hex, rgb, arbitrary values). Use theme tokens so light and dark mode keep working.

## Icons

- Use `lucide-react`, the icon library shadcn uses.

## Forms

- Use the shadcn `Form` / `Field` components, `Input`, `Select`, `Checkbox`, `Textarea`, etc.
- Show validation and errors with the form components' built-in message support.

## Dates

- Use the shadcn `Calendar` and `Popover` components for date selection.
- All date formatting must be done with `date-fns` (e.g. `format(date, "PPP")`). Do not use `toLocaleDateString`, `Intl.DateTimeFormat`, or hand-rolled formatting.
- Install it with `npm install date-fns` if it isn't already a dependency.

## Checklist Before Committing UI Changes

1. Is every interactive or visual element a shadcn component?
2. Did I avoid creating any new component files?
3. Were new shadcn components added via the CLI, not by hand?
4. Is all styling done with Tailwind utilities and theme tokens?
5. Are all dates formatted with `date-fns`?
